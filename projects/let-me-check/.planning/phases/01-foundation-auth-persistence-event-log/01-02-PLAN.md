<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device storage → app | The refresh token at rest on the device is a high-value secret |
| OAuth provider → app → Supabase | An attacker-controlled redirect/idToken must not grant a session |
| app bundle → secrets | Anything in the JS bundle is public |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-07 | Information Disclosure | session refresh token on device | mitigate | Session stored via SecureStore (Keychain/Keystore), never AsyncStorage/MMKV. Verified: `grep SecureStore app/lib/supabase.ts`; `grep -i AsyncStorage app/lib/supabase.ts` returns nothing |
| T-01-08 | Spoofing | Apple/Google sign-in | mitigate | Native idToken validated server-side by Supabase via `signInWithIdToken` (Supabase verifies the provider signature/nonce) — app does not self-assert identity |
| T-01-09 | Information Disclosure / Elevation | secrets in client bundle | mitigate | Only `EXPO_PUBLIC_SUPABASE_ANON_KEY` (RLS-protected, public-safe) is in the client; no service-role key; no Twilio creds (`grep -riq "twilio" app/lib/` is empty) |
| T-01-10 | DoS/Spoofing | phone OTP brute-force / SMS pumping | accept (this phase) | Throttling/expiry owned by Supabase + Twilio provider (not hand-rolled). E.164 + code-length validation at the boundary. Note for ops monitoring; deeper rate-limit tuning is a launch-phase concern |
| T-01-11 | Tampering | OAuth deep-link/redirect hijack | mitigate | Native idToken path avoids browser redirect entirely; if the documented browser fallback is ever used, the redirect URL must be allow-listed in Supabase and the app `scheme` set — flagged, not used by default |
</threat_model>
