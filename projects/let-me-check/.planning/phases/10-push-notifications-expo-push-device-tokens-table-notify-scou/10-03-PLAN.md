<objective>
Wire the client side: a `push.ts` helper that registers the device for push (permission + ExpoPushToken via the bundled EAS projectId, simulator-safe), upserts/deletes the token in `device_push_tokens`, calls it fire-and-forget after every sign-in and on sign-out, and adds the Scout `job-nearby` preference toggle to the notifications screen.

Purpose: The server can only push to devices that have registered a token. Registration must happen AFTER the auth session is confirmed (not on a screen mount — anti-pattern). This plan also resolves Open-Q1 (the Scout job-nearby pref key) by adding it to the existing notifications settings list rather than building a separate Scout screen.
Output: push.ts + green vitest, auth.ts wiring, and the job-nearby toggle.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> device_push_tokens | Authenticated client upserts/deletes its OWN token only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-10 | Tampering | client writing a token under another user_id | mitigate | upsert payload sets user_id from getUser(); RLS WITH CHECK (auth.uid()=user_id) (Plan 01) rejects any mismatch |
| T-10-11 | Information Disclosure | leaking the push token off-device | accept | The ExpoPushToken is a routing handle, not a secret; it only routes to this device's APNs/FCM registration and is RLS-scoped at rest |
| T-10-12 | Denial of Service | registration throwing and blocking sign-in/sign-out | mitigate | All registration/cleanup calls are fire-and-forget with .catch/try-swallow — never block the auth flow |
| T-10-13 | Tampering | token registered on a simulator producing junk rows | mitigate | Device.isDevice guard returns null on simulators (PUSH-12); no upsert occurs |
</threat_model>
