## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Scout screen → server (acceptCheck/markFilming/markDelivered) | The client requests claims/transitions; the server RPCs authorize (assigned scout only) |
| Scout open-list query → RLS | The dashboard can only read open + own checks; RLS confines the result |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering/Elevation | Two Scouts accept the same check (double-booking) | mitigate | acceptCheck -> accept_check atomic guarded UPDATE (0007); the loser gets 'already taken' and the dashboard refreshes. Proven by accept_check_atomic.test.sql + the on-device walk-through (Plan 04 Task 4). |
| T-02-03 | Elevation | A non-assigned Scout marks a check filming/delivered | mitigate | markFilming/markDelivered -> transition_check actor authz (v_uid = scout_id, 0007); a non-assigned caller raises. |
| T-02-04 | Information Disclosure | The dashboard enumerates all checks (incl. delivered/others') | mitigate | listOpenChecks selects only 'dispatching'; narrow Scout RLS (0009) exposes open + own only — the client cannot widen it. |
| T-02-05 | Tampering | Deliver with no clip / fake delivery | mitigate | markDelivered inserts the stub clip before transitioning; deliver-needs-clip guard (0007) backstops; clips_insert_assigned_scout RLS (0009) restricts who/when. |
</threat_model>
