<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client lib → server RPC | All state changes go through transition_check/accept_check; the lib must never UPDATE checks directly |
| Realtime channel → subscriber | Postgres Changes RLS-checks each event; only the owning Seeker receives their check's updates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10 | Tampering | A lib wrapper writes checks.status/scout_id directly (bypassing the server guards) | mitigate | All status changes route through rpc('transition_check'/'accept_check'); `! grep "from('checks').update"` is a hard acceptance check in Task 2. |
| T-02-11 | Information Disclosure | listOpenChecks leaks other seekers' checks | mitigate | Lib only `select * where status='dispatching'`; the narrow Scout RLS (0009) does the confinement server-side — the lib cannot widen it. |
| T-02-12 | Tampering | markDelivered transitions to delivered without inserting a clip | mitigate | markDelivered inserts the stub clip BEFORE the transition; the server deliver-needs-clip guard (0007) is the backstop; Task-1 spec asserts insert-before-transition. |
</threat_model>
