<objective>
STEP 5 of the 6-step plan (D-05): WIRE the proven blur module into the recording→upload flow at the single seam, behind a flag, with the privacy-safe fallback. The module is now known to work and be fast (Plans 01-04); this plan inserts `blurFaces` between "have the file" and "upload the file" so the BLURRED file is what uploads — raw never leaves the device on the happy path (D-04).

Purpose: Connect the de-risked module to the real flow without ever letting an incomplete/failed blur block the working upload OR deliver an unblurred face. Flag-gated (D-04): OFF = today's flow unchanged; ON = blur-before-upload with retry→pixelate→server-fallback on failure.
Output: submit() in clips.ts gains a 'securing' state that blurs the clip, swaps capturedPath→blurredPath, uploads the blurred file, deletes the raw on success; on 'failed' it retries then routes to the dormant server-side detect-and-hold (face-blur-check) so D-07 (no unblurred face delivered) always holds. filming.tsx shows "Securing your clip…". All behind BLUR_POST_RECORD_ENABLED (default false).
</objective>

Current flow (clips.ts useClipUpload.submit):
  setStatus('uploading')
  const { uploadUrl } = await requestUploadUrl(checkId, gpsArg, fraudSignals)
  await uploadWithRetry(localPath, uploadUrl, 4, onProgress)

New flow (flag ON), inserted BEFORE requestUploadUrl/upload:
  setStatus('securing')
  const result = await blurFaces(localPath)            // from app/lib/blur-native.ts
  // result.status: 'blurred' | 'no_faces' | 'failed'
  const pathToUpload = (result.status === 'failed') ? <fallback> : result.outputPath
  setStatus('uploading'); ... upload pathToUpload ...
  if blurred && upload ok: delete the raw capturedPath (no unblurred copy lingers — Pitfall 6)

ClipUploadStatus currently: 'idle'|'uploading'|'processing'|'error' — add 'securing'.

Fallback (06-RESEARCH-BLUR-V2 Fallback section, in order):
  1. retry blurFaces once (transient codec/memory failures often pass on retry)
  2. retry in pixelate mode (cheaper/more robust)
  3. only if both fail → route THIS clip to the dormant server-side detect-and-hold
     (face-blur-check / mux-webhook blur gate from Phase 6) so it is held, not delivered unblurred.
     This is the <1% escape hatch, NOT the normal path (D-04). Never upload the raw file as if blurred.

Existing dormant net (Phase 6, keep as last resort): supabase/functions/face-blur-check + mux-webhook blur gate (fires filming->blur_review when blur_enabled). market_config.blur_enabled default FALSE.
