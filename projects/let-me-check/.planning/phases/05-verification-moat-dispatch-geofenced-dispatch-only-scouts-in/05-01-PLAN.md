**8. reset_check_for_redispatch RPC (service-role-only writer of scout_id on re-dispatch).** Per RESEARCH Re-dispatch section:
```sql
create or replace function public.reset_check_for_redispatch(p_check_id uuid)
returns check_status
language plpgsql security definer set search_path = public
as $$
declare v_uid uuid := auth.uid(); v_from check_status;
begin
  -- Only the system (service role, auth.uid() IS NULL) may reset for re-dispatch.
  if v_uid is not null then raise exception 'reset_check_for_redispatch: system only'; end if;
  select status into v_from from public.checks where id = p_check_id for update;
  if not found then raise exception 'reset_check_for_redispatch: check % not found', p_check_id; end if;
  -- Mark the latest clip rejected (Pitfall 5: avoid two live clips).
  update public.clips set status = 'rejected'
    where check_id = p_check_id
      and id = (select id from public.clips where check_id = p_check_id order by created_at desc limit 1);
  -- Null scout_id (re-open) + move back to dispatching via the legal edge.
  update public.checks set scout_id = null where id = p_check_id;
  perform public.transition_check(p_check_id, 'dispatching',
    jsonb_build_object('reason', 'gps_rejected'));
  perform public.log_event('check.redispatched', 'check', p_check_id,
    jsonb_build_object('reason', 'gps_rejected', 'from', v_from));
  return 'dispatching';
end;
$$;
```
NOTE: transition_check's `dispatching` actor-authz currently requires `v_uid = seeker`. Since this RPC runs as service role (auth.uid() null) and calls transition_check internally (still auth.uid() null), the existing `elsif p_to='dispatching' and v_uid is distinct from v_seeker` guard would THROW for a null uid. To keep transition_check the sole status writer, REPLACE transition_check in THIS migration (copy the 0010 body verbatim) and relax ONLY the dispatching branch to also allow the system: `elsif p_to = 'dispatching' and v_uid is not null and v_uid is distinct from v_seeker then raise ...` (add `v_uid is not null and`). Document this as the only change vs 0010.

## Trust Boundaries

| Boundary | Description |

| Scout client → scout_locations | Untrusted lat/lng written by a Scout for their OWN row only |
| Service role → checks.scout_id reset | System-only re-dispatch path (auth.uid() must be null) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | scout_locations row | mitigate | RLS: `auth.uid() = scout_id` on insert/update/select; a Scout cannot write or read another's location |
| T-05-02 | Elevation of Privilege | reset_check_for_redispatch | mitigate | Function raises unless `auth.uid() IS NULL` (service role only); keeps scout_id null-reset off the client |
| T-05-03 | Tampering | checks.status via relaxed dispatching edge | mitigate | transition_check still requires `v_uid = seeker` for a HUMAN; only null-uid system is additionally allowed (one-line, documented change) |
| T-05-04 | Input Validation | distance_m / is_in_no_film_zone | mitigate | NaN/null guards return null/false rather than passing silently (V5) |
| T-05-05 | Spoofing | lng/lat swap producing wrong fence result | mitigate | pgTAP Test asserts ST_MakePoint(lng,lat) order incl. a deliberate-swap negative case |
