Edge fn shape (from stripe-refund/index.ts):
```ts
import { getStripeClient } from "../_shared/stripe.ts";
import { authedClient, serviceClient } from "../_shared/supabase.ts";

export interface XInput { callerId: string | null; body: {...}; }
export interface XDeps { stripe: Stripe; svc: SupabaseClient; }
export async function handleX(input: XInput, deps: XDeps): Promise<Response> { ... }

if (import.meta.main) {
  Deno.serve(async (req) => {
    const authed = authedClient(req);
    const { data: userData } = await authed.auth.getUser();
    const callerId = userData?.user?.id ?? null;
    const body = await req.json();
    const stripe = await getStripeClient();
    const svc = serviceClient();
    return await handleX({ callerId, body }, { stripe, svc });
  });
}
```
Auth: callerId from bearer (verify_jwt=true at deploy — these are user-facing functions, NOT webhooks). 401 if null.

stripe-refund hard truth (confirmed from source lines 90-160): for an `authorized` (uncaptured) payment with reasonCode 'never_delivered', stripe-refund does NOT cancel the PI — it inserts a refund_requests row and, on auto_approve, calls `stripe.refunds.create({payment_intent})` which FAILS on an uncaptured PI. Therefore trouble-report and the sla-sweeper MUST call `stripe.paymentIntents.cancel(pi)` directly to release an uncaptured hold. Do NOT route uncaptured holds through stripe-refund.

stripe-capture transfer pattern (D-09 platform-funded, the model for no-fault pay): `stripe.transfers.create({ amount, currency, destination: scout_account_id, transfer_group, metadata })` with NO source_transaction = funded from platform balance. NEVER reverse a transfer on refund (D-08).

log_event RPC: `svc.rpc('log_event', { p_event_type, p_subject_type, p_subject_id, p_context })` — match the positional names used in stripe-refund (`p_event_type` + `p_context`; pass p_subject_type/p_subject_id where the existing calls do).

Tables: payments(check_id, stripe_payment_intent_id, status, scout_amount, currency); scout_stripe_accounts(scout_id, stripe_account_id, payout_speed, charges_enabled, payouts_enabled); checks(id, status, scout_id, seeker_id, tier, stripe_payment_intent_id).

transition_check RPC: `svc.rpc('transition_check', { p_check_id, p_to, p_context })`. BLOCKER 1: trouble-report runs as SERVICE ROLE (auth.uid()=NULL). The `cancelled` actor guard (`v_uid is distinct from v_seeker`) is TRUE for a NULL uid and ALWAYS raises "only the seeker may cancel" — so trouble-report MUST drive `'no_scout'`, NOT `'cancelled'`. The `no_scout` guard uses the relaxed `v_uid is not null` form and permits service role. Plan 01 Task 2 adds the `assigned->no_scout` + `filming->no_scout` transition-validity edges this depends on.

Stripe balance for instant net (Stripe SDK, _shared/stripe.ts getStripeClient):
```ts
const balance = await stripe.balance.retrieve(
  { expand: ['instant_available.net_available'] },
  { stripeAccount: acctId });
const availableCents = balance.available.find(b => b.currency === 'usd')?.amount ?? 0;
const instantNetCents = balance.instant_available?.find(b => b.currency==='usd')?.net_available?.[0]?.amount ?? availableCents;
```

create or replace function public.scout_earnings_weekly(p_scout_id uuid)
returns table(day date, cents bigint)
language sql security definer set search_path = public as $$
  select date_trunc('day', c.updated_at)::date as day, sum(p.scout_amount)::bigint as cents
  from public.checks c join public.payments p on p.check_id = c.id
  where c.scout_id = p_scout_id and p.status in ('transferred','captured')
    and c.updated_at >= now() - interval '7 days'
  group by 1 order by 1;
$$;
create or replace function public.scout_earnings_totals(p_scout_id uuid)
returns table(total_cents bigint, total_clips bigint)
language sql security definer set search_path = public as $$
  select coalesce(sum(p.scout_amount),0)::bigint, count(*)::bigint
  from public.checks c join public.payments p on p.check_id = c.id
  where c.scout_id = p_scout_id and p.status in ('transferred','captured');
$$;

<threat_model>
## Trust Boundaries
| Boundary | Description |
|----------|-------------|
| client → Edge fn (bearer) | untrusted Scout JWT; callerId is the only identity source |
| Edge fn → Stripe | platform secret in Deno.env; moves real money |
| Edge fn → Postgres (service role) | bypasses RLS; ownership must be enforced in code |

## STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05 | Spoofing | Scout claims trouble on another's check | mitigate | check.scout_id === callerId gate before any action (403) |
| T-07-06 | Tampering (double-refund) | trouble-report cancelling an already-captured/refunded payment | mitigate | only cancel when payment.status === 'authorized'; transition_check('cancelled') state guard blocks a second cancel |
| T-07-07 | Tampering (double-payout) | retry creates a second Scout Transfer or duplicate payout | mitigate | trouble-report idempotency via event_log lookup; payout logs payment.payout_initiated before create |
| T-07-08 | Tampering (premature capture) | wrong rail captures an authorized hold | mitigate | trouble-report uses paymentIntents.cancel (release), never capture or refund of an uncaptured PI (Pitfall 4) |
| T-07-09 | Tampering (debit-balance) | instant payout using gross overdraws Scout (2% fee debited after) | mitigate | instant amount bounded by instant_available.net_available; reject if requested > net (Pitfall 5) |
| T-07-10 | Information Disclosure (IDOR) | reading/withdrawing another Scout's earnings | mitigate | scoutId = callerId only; no body-supplied scoutId in scout-earnings or stripe-connect-payout |
| T-07-11 | Repudiation | money move with no trail | mitigate | log_event on every cancel, Transfer, payout_initiated, refund |
</threat_model>
