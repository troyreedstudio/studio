<objective>
Wire the money-moving server logic. `stripe-capture` captures the held PaymentIntent on delivery and creates a SEPARATE Transfer to the Scout's Connect account (D-03/D-04), with the D-09 fallback (capture fails -> Scout still paid from platform balance, Seeker blocked). `stripe-webhook` mirrors `mux-webhook` exactly: verify the Stripe signature against the raw body BEFORE trusting anything, then handle disputes (PAY-05), account.updated (Scout onboarding state), payout events, and PI cancellation. The client never captures.

Purpose: This is where the Seeker is actually charged and the Scout actually gets paid — the core money movement. Separate charges + transfers (not destination charges) is what lets a refund leave the Scout's pay intact (D-08, executed in Plan 07).
Output: stripe-capture + stripe-webhook edges, each with a Deno test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe → stripe-webhook | Untrusted POST; signature proven over raw body before any action |
| service role → capture/transfer | Only the system (service role) moves money; no human caller |
| dispute event → ledger | A dispute must never reverse the Scout's transfer (D-08) |
